## フェーズ1：エンジン（ゲームのルール部分）

### 1. 設計の方針

- ルールの処理はすべて `web/src/engine/` に置き、**ReactにもブラウザにもHTMLにも依存しない、純粋なTypeScript**で書きました。
  - Expoへ変換するときは、このフォルダを**ほぼそのままコピー**できます。
- **状態を直接書き換えず、新しい状態を返す**書き方（イミュータブル）にしました。

  ```ts
  const next = applyAction(hand, { type: 'call' }); // hand 自体は変わらない
  ```

  - Reactは「新しいオブジェクトになったか」で再描画を判断するので、この書き方と相性が良いです。
  - 前の状態を残しておけば、そのまま「1手戻す（Undo）」に使えます（フェーズ3で利用）。
- **現在時刻は引数で受け取る**ようにしました（`startHand(t, now)` など）。テストで「20分後」のような状況を、実際に待たずに確かめられます。

### 2. 作ったファイル

| ファイル | 役割 |
|---|---|
| `types.ts` | 型定義（設定、プレイヤー、1ハンドの状態、アクションなど） |
| `clone.ts` | 状態の深いコピー（JSONを使う方法なのでReact Nativeでも動く） |
| `pots.ts` | メインポット・サイドポットの計算、引き分け時の分配 |
| `hand.ts` | 1ハンドの進行：ブラインドの徴収、手番、アクションの検証、ストリートの進行、ショーダウン |
| `positions.ts` | ボタン・SB・BBの位置決め（デッドボタン、ヘッズアップ） |
| `clock.ts` | ブラインドタイマー、レベル番号、リエントリーの受付期間 |
| `presets.ts` | WSOP風のブラインド表のプリセット3種類 |
| `tournament.ts` | トーナメント全体：ハンドの開始・終了、脱落、リエントリー、途中参加、順位 |
| `index.ts` | 画面側から読み込むための窓口 |
| `*.test.ts` | テスト（5ファイル・46件） |

### 3. 実装したルール

| ルール | 実装した内容 | 根拠 |
|---|---|---|
| ブラインドとBBアンティ | BBのチップが足りないときは、ブラインドを先に払い、残りをアンティにする。アンティはメインポットに入る | 用語集、Rule 86 |
| デッドボタン | BBは必ず次の人へ進む。前回のBBが脱落したらSBなし、前回のSBが脱落したらボタンは空席に置く | Rule 85 |
| ヘッズアップ | SBがボタンを持つ。3人から2人になるとき、同じ人が2回続けてBBにならない | Rule 87 |
| アクション順 | プリフロップはBBの左から、フロップ以降はボタンの左から | Rule 72・93 |
| ミニマムベット／レイズ | 最小ベットはBB、最小の上乗せは直前のフルレイズの上乗せ額 | Section VIII、Rule 96 |
| ショートオールイン | フルレイズに届かないオールインでは、すでにアクションした人はレイズできない。オールインが続いて合計がフルレイズ以上になれば、レイズの権利が戻る | Rule 96 |
| 返却 | 誰もコールしていない分は本人に返す | 一般知識 |
| サイドポット | 出した額ごとに層に分けて、参加できる人を決める | Rule 74 |
| 引き分け | 最小チップ単位で分け、端数はボタンの左に近い勝者へ | Rule 73 |
| 最初に見せる人 | リバーで最後にベット／レイズした人。いなければボタンの左から | Rule 72 |
| オールイン後の進行 | 賭けが終わったら、残りのボード（例：ターン・リバー）を表示してショーダウンへ | Rule 70 |
| レベルの切り替え | 新しいブラインドは次のハンドから。休憩中にハンドを始めたら直前のレベル | Rule 79 |
| リエントリー | チップ0の人だけ、満額で再参加できる。上限回数と締切レベルを設定できる | Rule 13 |
| 受付の締切 | 締切レベルの終わりまで。直後が休憩なら休憩明けまで | Rule 12 |
| 途中参加 | 受付期間中なら、空いている席に満額で追加できる | Rule 12・14 |
| 順位 | 後に脱落した人ほど上位。同じハンドで脱落したら、開始時のチップが多い人が上位 | Rule 126 |

### 6. ルールの解釈について（判断したこと）

WSOPルールに書かれていない点、または解釈が分かれる点は、次のように決めました。

| 場面 | 決めたこと |
|---|---|
| BBのチップがBBの額に足りない | 他の人がコールする額はBBの額のまま。足りない分はサイドポットで調整する |
| チェックした後に、BB未満のオールインのベットが来た | すでにアクションしている（チェック）ので、レイズはできない（Rule 96の文言どおり） |
| リエントリーした人の席 | 同じ席に戻る（ホームゲームで使いやすいように） |
| 途中参加の受付期間 | リエントリーと同じ期間 |

### 学んだこと

- **ロジックと画面を分ける**と、ルールのテストが画面なしで書け、Expoへの移行も楽になります。
- **純粋関数**（同じ入力なら必ず同じ結果を返し、外の状態を変えない関数）で書くと、テストがとても簡単になります。時刻のように毎回変わる値は、引数で受け取るのがコツです。
- TypeScriptの**判別可能なユニオン型**（`{ type: 'fold' } | { type: 'raise'; to: number }`）を使うと、`switch (action.type)` で分けたときに、それぞれの場合で使えるプロパティを型チェックしてくれます。

## フェーズ2：画面

### 1. 動かし方

```bash
cd web
nvm use
npm run dev
```

ブラウザで http://localhost:5173/ を開きます。スマホで見るときは、開発者ツールのデバイス表示（幅390px程度）にすると実際の見た目に近くなります。

### 2. 画面の流れ

```
設定画面 ──スタート──▶ テーブル画面 ──（残り1人・受付終了）──▶ 結果画面
                         │                                      │
                         ├ ハンドの開始                            └ 新しいトーナメント → 設定画面へ
                         ├ アクション入力（ベッティング中）
                         ├ 勝者の選択（ショーダウン）
                         ├ ハンドの結果 → 次へ
                         └ プレイヤー・順位（リエントリー、途中参加）
```

画面の切り替えには、ルーター（URLで画面を切り替える仕組み）を使っていません。状態を見て、表示する画面を決めています（`App.tsx`）。

- トーナメントがない → 設定画面
- 終了している（`isFinished`）→ 結果画面
- それ以外 → テーブル画面

### 4. 主な機能

**設定画面**
- WSOP風プリセット3種類から選び、ブラインド表を1行ずつ編集できる（レベル・休憩の追加と削除）
- 初期スタック、最小チップ、リエントリー（締切レベル、最大エントリー数）
- プレイヤーは2〜10人。最初のボタンは「ランダム」か指定
- 入力に問題があるとエラーを表示し、スタートできない

**テーブル画面**
- タイマー：開始／停止、前後のレベルへの移動。最初のハンドを始めると自動で動き出す
- レベルが上がっても、プレイ中のハンドは前のレベルのまま（「次のハンドから新レベル」と表示。Rule 79）
- ハンドとハンドの間は、**次のハンドのD／SB／BBの位置**を先に表示する。デッドSB・デッドボタンも空席に表示する
- アクション入力：
  - ルール上できない操作はボタン自体を出さない（例：チェックできないときはコールだけ表示）
  - クイックボタン（Min、½ポット、ポット、オールイン）、スライダー、±（BB単位）、金額の直接入力
  - チップが足りないときのコールは「オールイン 24,600」のように表示
- ショーダウン：
  - オールインで賭けが終わったら「全員の手札を表向きにして、ターン・リバーを開いてください」と表示（Rule 70）
  - そうでなければ「最初に見せる人」を表示（Rule 72）
  - ポットごとに勝者を選ぶ。メインポットで選んだ人は、その人が参加しているサイドポットにも先に選んでおく（変更できる）
- ハンドの結果：ポットごとの獲得額、各プレイヤーの増減、脱落者
- プレイヤー・順位：チップの多い順の順位表。脱落者はリエントリーボタン（受付期間中のみ）。空いている席への途中参加

### 5. 確認したこと

型チェック、Lint、テスト（46件）、本番用ビルドがすべて通ることを確認しました。

さらにPlaywright（ブラウザを自動で操作するツール）で、スマホと同じ画面幅（390px、360px）で実際に操作して確認しました。

- 4人：リンプ → レイズ → コール → フロップでオールイン → ターン・リバーはチェック → 勝者選択 → 結果 → 脱落 → 次のハンドでデッドSBが正しく表示される
- 2人：ハンド中にレベルを上げる → 「次のハンドから新レベル」の表示 → オールイン → 結果画面

**見つけて直した問題**

| 問題 | 対応 |
|---|---|
| 左右の席が画面の端からはみ出す | 席の配置を内側に寄せた |
| ブラインド表の入力欄で数字の末尾が切れる | 数値入力の上下ボタン（スピンボタン）を消し、余白を詰めて右寄せにした |
| タイマーの⏮⏸⏭や🏆の絵文字が、フォントによって表示されない | 文字（«、開始／停止、»）に変えた |
| 描画のたびに変数を書き換えていた（Lintの警告） | エンジンの `levelNumber` 関数を使うようにした |

- 1手戻す（Undo）
- 自動保存（ブラウザを閉じても続きから再開できる）

### 学んだこと

- **`useReducer`**：状態を変える処理を、`(今の状態, 操作) => 次の状態` という1つの関数（reducer）にまとめる仕組みです。画面は「何をしたか」（`{ type: 'act', action }`）を `dispatch` で送るだけになります。reducerはReactに依存しない普通の関数なので、Expo版でもそのまま使えます。
- **`key` で部品を作り直す**：`<ActionPanel key={手番ごとに変わる値} />` のように書くと、手番が変わるたびに部品が新しく作られ、金額入力の初期値が毎回ミニマムレイズに戻ります。`useEffect` で値をリセットするより簡単で、バグも起きにくい方法です。
- **表示用の値は状態から計算する**：タイマーの残り時間は保存しておかず、「最後に計算した時刻」と「現在時刻」から毎回計算しています。保存する値が少ないほど、ずれが起きにくくなります。
- **Expoを意識した書き方**：レイアウトはFlexboxと絶対配置（席の配置）だけにしました。CSS Gridなど、React Nativeにない機能は使っていません。数字の区切りも `toLocaleString` を使わず自分で書いたので、どの環境でも同じ表示になります。

## フェーズ3：仕上げ

### 1. 追加した機能

| 機能 | 内容 |
|---|---|
| **1手戻す（Undo）** | 画面下の「↶ 戻す」で直前の操作を取り消す。アクション、ショーダウンの勝者選択、ハンドの開始・終了、リエントリー、途中参加が対象。最大50手まで戻れる |
| **自動保存** | 操作のたびにブラウザ（localStorage）に保存する。ページを閉じても再読み込みしても、続きから再開できる。Undoの履歴も保存するので、再読み込みの後も戻せる |
| **レベルアップの通知** | レベルが上がると、音（3回のビープ音）、振動（対応している端末のみ）、画面上部のバナーで知らせる。音はタイマーの「音：ON／OFF」で切り替えられる（設定は保存される） |
| **残り1分の表示** | 次のレベルまで1分を切ると、残り時間がオレンジ色になる |
| **ハンド履歴** | 「履歴」から、これまでのハンドとプレイ中のハンドを新しい順に表示する。ストリートごとのアクション（例：レイズ 600）と、誰がいくら取ったか |
| **画面のスリープ防止** | テーブル画面を開いている間は、画面が消えないようにする（Wake Lock API。対応しているブラウザのみ） |
| **スマホ向けの調整** | ダブルタップで拡大されないようにした。iPhoneのノッチやホームバーに重ならないようにした |

### 2. Undoの仕組み

reducerが「今の状態」とは別に「過去の状態の一覧（`past`）」を持ちます。

```
操作するたびに：  past = [...past, 今の状態]、今の状態 = 新しい状態
戻すとき：      今の状態 = past の最後、past = 最後を除いたもの
```

- エンジンが「前の状態を書き換えずに新しい状態を返す」作り（フェーズ1）なので、前の状態をそのまま取っておくだけで実現できました。
- **タイマーは戻しません**。実際に経過した時間は取り消せないので、戻したときもタイマーは今の状態のままにしています。タイマーの操作自体もUndoの対象外です。
- **メモリの節約**：終わったハンドの履歴は二度と変わらないので、過去の状態どうしでコピーせずに共有するようにしました（`tournament.ts` の `cloneTournament`）。

### 3. 保存の仕組み

- 保存する形式に `version` を付け、形式が合わないデータは読み込まないようにしました。後でデータの形を変えたときに、古いデータでアプリが壊れるのを防ぐためです。
- **保存サイズの工夫**：過去の状態をそのまま保存すると、ハンド履歴が最大50回も重複します。過去の状態の履歴は必ず今の履歴の先頭部分と同じなので、**件数だけを保存**し、読み込むときに今の履歴から切り出して復元しています（`persistence.ts`）。
- タイマーは「最後に計算した時刻」を保存しているので、アプリを閉じている間に経過した時間もきちんと進みます。

### 7. Androidの実機で確認する手順（Expo Go）

#### 準備（最初の1回だけ）

1. スマホに Google Play から **Expo Go** を入れる
2. https://expo.dev/signup で Expo のアカウントを作る（無料。あとでストア用のアプリを作る EAS Build でも使う）
3. PC（WSL）でログインする。**`--no-browser` を付けて、ターミナルで入力する**（理由は下の「つまずいたこと」）
   ```bash
   cd ~/poker-app/expo-app
   npx expo login --no-browser   # メールアドレス（またはユーザー名）とパスワードを入力
   npx expo whoami               # ユーザー名が出ればログインできている
   ```
4. スマホの Expo Go にも、同じアカウントでログインする

#### 毎回の起動

```bash
cd ~/poker-app
nvm use
npm run start:app -- --tunnel
```

表示されたQRコードを、Expo Go の「Scan QR code」で読み取る。止めるときは Ctrl+C。

- **`--tunnel`**：WSL はWindowsの中の別のネットワークで動いているため、同じWi-Fiでもスマホから直接つながらないことが多い。インターネット上の中継（トンネル）を通してつなぐ
- **`--`**：npm に「ここから後ろは中のコマンド（`expo start`）に渡して」と伝える区切り

#### つまずいたこと（2026-11-03）

| 症状 | 原因 | 対処 |
|---|---|---|
| QRコードが表示されない | ルートのスクリプトが `npm run start -w expo-app` だったため、後ろに付けた `--tunnel` を中の npm が自分の設定として受け取り、Expo まで届いていなかった | スクリプトを `npm run start -w expo-app --` に変え、引数がそのまま Expo に渡るようにした |
| `You're not logged in to your Expo account` | 新しい Expo CLI（SDK 58）の `--tunnel` は、ngrok ではなく **Expo 公式のトンネル**を使い、ログインが必要 | Expo のアカウントを作ってログインする |
| `Missing script: "start:app"` | `cd` の打ち間違いで `expo-app/` にいたまま実行した。`start:app` はルートの package.json にだけある | ルート（`~/poker-app`）で実行する。`expo-app/` の中なら `npm run start -- --tunnel` |
| ブラウザでログインしたのに `Not logged in` のまま／`cmd.exe ... exited with non-zero code: 1` | Expo CLI は何も指定しないとブラウザでログインしようとする。WSL から Windows のブラウザを開くとき、URL の `&` を `cmd.exe` が「コマンドの区切り」と解釈して失敗する（`-u` でユーザー名を渡してもブラウザ方式になる） | `npx expo login --no-browser` でターミナルからログインする |

ログインしたくない場合は `npm run start:app -- --tunnel ngrok` で、以前からある ngrok のトンネルも使える（初回は `@expo/ngrok` のインストールを聞かれる）。

#### 実機で見てほしいところ（Web では確認できない部分）

- 見た目・文字の大きさ・スクロール
- 数字の入力欄で数字キーボードが出るか
- 「戻る」：ホーム以外ではホームへ戻り、ホームではアプリが閉じる
- テーブル画面で画面が自動で消えない
- レベルが上がったときの音・振動（「»」でレベルを進めて確認）
- アプリを完全に閉じて開き直しても「続きから再開」できる

### 学んだこと

- **React Native の部品は、Web とスマホで同じコードが動く**：react-native-web のおかげで、`<View>` や `<Pressable>` がブラウザでは HTML になる。ただし、古い書き方（`accessibility*`）のように Web に出力されないものもあるので、Web でも確認するのが大事
- **非同期の読み込み**：スマホの保存領域（AsyncStorage）は読み込みに時間がかかる。スプラッシュ画面を出したまま読み込みを済ませると、利用者に空の画面を見せずに済む
- **開発モードと本番用ビルドの違い**：開発モードでしか出ないエラーもある。本番用ビルドでも確認すると、本当の問題かどうかを見分けられる
- **雛形のファイルも中身を確認する**：`LICENSE` のように、そのまま公開すると誤解を招くものが含まれていることがある
- **npm スクリプトへの引数の渡し方**：`npm run X -- 引数` の引数は X のコマンドの最後に付くだけ。X の中でさらに npm を呼ぶときは、中にも `--` が必要
- **エラーメッセージとツールのソースを読む**：Expo CLI のエラーには代わりの方法（`--tunnel ngrok`）が書かれていた。`--no-browser` は `node_modules/@expo/cli` のソースを読んで見つけた。ツールの仕様は版によって変わるので、古い情報をうのみにしない

| 単数形・複数形・順位 | 言語ごとに必要な形を用意した。ロシア語は4通り（1 раздача／2 раздачи／5 раздач…）、フランス語の順位は「1er・2e」、スペイン語などは100万以上の形もある |
| スマホ版の Intl の補い | i18next は数え分けに `Intl.PluralRules` を使う。スマホの JavaScript エンジン（Hermes）にはない可能性があるので、`@formatjs/intl-pluralrules` などを「ないときだけ補う」形で入れた（`expo-app/index.ts` の先頭） |
| アプリ名 | `app.json` の `locales` に12言語。Android は `values-b+zh+Hans` のような言語別フォルダ、iOS は `zh-Hans.lproj` に書き出される（prebuild で確認） |
| Web のフォント | 漢字は言語によって字形が違うので、`:lang(ja)`・`:lang(zh-Hans)` などで言語ごとのフォントを優先する。ブラウザのタブのタイトルも言語に合わせた |

### 学んだこと

- **言語によって「数」の扱いが違う**：英語は「1 と それ以外」だが、ロシア語は4通り、日本語・中国語は1通り。i18next は `Intl.PluralRules` が返す種類（one／few／many／other）に合わせて `_one`・`_few` などのキーを選ぶ
- **数字の書き方も言語ごとに違う**：桁区切りは「,」「.」「空白」と言語で違う。フランス語の空白は、行の途中で折り返さない空白（NBSP）を使う
- **同じ漢字でも字形が違う**：日本語のフォントで中国語を表示すると、中国の人には違和感のある字形になる。`lang` 属性と `:lang()` で切り替える
- **長い言語で画面を確かめる**：ドイツ語・フランス語・ロシア語は英語より長く、ボタンやタイマー欄が崩れやすい。スクリーンショットを並べて見比べると見つけやすい
